# 目的と受け入れ条件

目的は、自分のOSSを公開・配布する前に、依存ライセンスの条件と未確認事項を把握し、対応漏れを防ぐことです。終了コード0を作ることや、個別ライセンスを補正して通すことを成功基準にはしません。

## 利用場面と合格条件

| 利用場面 | 合格条件 | 現状と検証方法 |
| --- | --- | --- |
| 検査範囲を決める | 何を検査したか・何を検査していないかが結果から分かる | インストール済みPython配布物を対象。ルート・extras・環境マーカーを固定し、期待する依存一覧と照合。ソース内コピー・OS/ROS/C++依存は範囲外 |
| 方針への適合を確認する | 明示した許可・禁止ルールで判定し、未設定なら「方針確認済み」と表示しない | AND/OR/例外・禁止優先を試験。未設定の結果は棚卸しとして区別する |
| 未確認を見つける | 不明な識別子・自由文・根拠不足を許可へ推測変換しない。元の値と理由を残す | SciPyやClassifierのみの配布物を未確認ケースに使う。補正を加えた場合も版と根拠を追跡できること |
| 配布前の対応を確認する | 必要な証拠の有無と、利用者が確認すべき義務・未対応が分かる | 現状はファイル収集と欠落の検出まで。条件からの義務抽出、表示・ソース提供等の対応完了の管理は未実装。配布準備完了とは表示しない |
| 依存を更新する | 新規依存・ライセンス変更・補正の失効をレビュー対象にできる | 基準を固定し、追加・削除・表記/判定変更・版変更を試験。従来の違反も再判定する |

## 優先順位

1. 棚卸し・方針判定・証拠収集・配布準備の状態を混同しない表示と機械可読データにする。
2. 配布物に何を含めるかを明示し、必要な表示・証拠と対応状況を追跡する設計を固める。ファイルが存在するだけでは完了にしない。
3. プロジェクトごとの実際の配布方針で受け入れ試験を行う。利用者の方針を推測して許可リストを作らない。

配布物・構成要素・必要な対応・証拠を結びつける [設計案と検証方法](DISTRIBUTION_REVIEW_DESIGN.md) を用意しています。これは記録の設計検証で、CLIから配布準備を判定する実装ではありません。

[ソース検査モード](SOURCE_INVENTORY.md) は固定コミットの追跡ファイルとパスに基づく候補を出力し、すべて未確認の記録へつなげます。第三者素材の同定・適用義務の決定・履行の検証は人の確認が必要です。

最初の修正では、方針未設定の `inventory-only` と設定済みの `policy-evaluated` を区別し、HTML・Markdownでは棚卸しを方針確認の成功として表示しません。`status` の既存値は互換性のため残し、JSON・CSV・ターミナルにも `assessment` を付加します。証拠収集と義務対応の完了を結びつける機能はまだありません。基準JSONには検査全体のポリシー・対象条件のスナップショットを持たせていないため、比較条件の同一性を自動で保証できない点も残る課題です。

## Calibrexでの検証の位置づけ

- コアとextrasの依存集合を期待値と照合し、検査範囲の漏れ・混入を検証する。
- SciPyの自由文・同梱バイナリ、mcapの証拠欠落を、未対応を正しく残せるかの試験に使う。
- lz4・mcapの補正は根拠と更新時の失効の試験に使う。補正後に不明件数が減ったことだけで成功とはしない。
- Calibrexの配布方針・対象成果物・必要な義務対応を確定していない現状では、全体を「配布可能」と評価しない。

既存の実プロジェクト検証・CIは技術的な回帰検証として維持します。ユーザーテストでは導入時間だけでなく、検査範囲・方針判定・残る未対応を利用者が正しく説明できるかも確認します。
