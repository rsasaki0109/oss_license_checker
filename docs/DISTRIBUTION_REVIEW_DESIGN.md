# 配布対応を追跡する設計案

目的は、必要な対応の漏れと、根拠のない完了扱いを防ぐことです。この段階はデータモデルと受け入れ条件の設計で、既存CLIから配布可否を判定する機能は追加していません。

## 配布単位を先に決める

同じPython依存でも、ソースのみの公開、依存を利用者が取得するwheel、依存も含むコンテナでは、配布物に含まれる内容が異なります。インストール済み依存の一覧から、配布への同梱を自動で推定しません。

配布単位には識別子・形態・説明・スコープ確認の有無を持たせます。実ファイルができたら、そのハッシュを結びつけます。Calibrexは利用者の指定で「ソース公開のみ」としました。例は `kind: source` ですが、公開するパスと第三者素材の確認が残るため `scope_confirmed: false` のままです。配布形態を決めたことと、内容の確認完了を分けます。

## 記録するもの

| 記録 | 主な項目 | 分離する理由 |
| --- | --- | --- |
| 配布物 | 形態、対象範囲の確認、実ファイルのハッシュ | どの成果物に対する確認かを固定する |
| 構成要素 | 名前・リビジョン・種別（Python配布物/ソース/データ等）、同梱/外部取得/不明、判断の根拠、ライセンス確認状態 | 実行時依存、コピーされたコードやデータ、配布物への同梱を区別する |
| 必要な対応 | 対象要素、対応内容、適用根拠、状態、担当者と確認日時、証拠参照 | 識別子や収集結果と、実際の対応を区別する |
| 証拠 | 取得した本文、ソース参照、配布物の検査記録、履行記録、取得元・ハッシュ | 本文の存在だけで配布対応済みにしない |

対応内容の種類はライセンス本文の同梱、著作権表示、NOTICE、ソース提供、再リンク対応、ライセンス・範囲の確認などです。現段階では、識別子だけから網羅的な義務を自動生成しません。人が条件と適用根拠を確認して記録します。

## 状態と根拠

- `needs_review`：何が適用されるか、対応内容を確定していない。
- `todo`：必要な対応を特定したが、履行を確認していない。
- `done`：特定した対応の履行を、対象配布物と証拠に結びつけて記録した。
- `not_applicable`：その配布物では適用されないことを、理由と証拠で記録した。
- `blocked`：判断や対応を進めるための情報・作業が不足している。

`done` / `not_applicable` は、配布範囲の確認、担当者・確認日時・証拠参照を必須にします。この設計案では、閉じる記録を特定の配布物ハッシュと、その配布物の検査・履行記録に結びつけます。新しい配布物では古い証拠のハッシュが合わないため、そのまま完了にできません。

証拠の取得元が上流LICENSEであることと、そのLICENSEを対象コンテナへ適切に同梱したことは別の事実です。また「対象外」は単なる除外スイッチではありません。同梱が不明なままでは対象外にできません。

## Calibrexの例

[設計用の記録](../examples/validation/calibrex/distribution-review.draft.json) は、実在する検証結果と「ソース公開のみ」の方針を使っています。実際の公開対象パス、第三者素材の権利確認は未完了です。

| 対象 | 現在の観測 | 記録する未対応 |
| --- | --- | --- |
| 配布範囲 | ソース公開を選択。公開するパス・内容の最終確認は未完了 | 第三者コード・データを含む対象範囲を固定する |
| mcap | 実行時依存。上流MIT本文は確保 | ソースへのコピーの有無を確認。wheelの欠落をそのままCalibrexのソース公開の未履行とは扱わない |
| SciPy | 実行時依存。Linux wheelの条件は収集済み | 実際にソースやバイナリを含めるかを確認。依存していることだけでバイナリ配布の義務を課さない |
| comma2k19由来の素材 | `docs/assets/evidence-demos/source/comma/` にコード・データ・LICENSE・取得記録がある | 公開する内容の条件、適用範囲、表示を確認する |
| KITTI形式のfixture | manifestは実録データではなく合成fixtureと明記 | 名前から実データと誤認せず、生成元と権利を確認する |

例はこの5点の未対応を示す抜粋です。Calibrexの全ソース・依存18件すべての義務確認を済ませた記録ではありません。[ソース範囲の観測](../examples/validation/calibrex/source-scope-observations.json) には固定コミットの追跡ファイル一覧の件数・ハッシュと、追加確認の候補を記録しました。パスの探索と一部本文の確認であり、コピーされたコードや素材を網羅的に検出したものではありません。

## 設計を検証する方法

```bash
python -m pip install -e '.[test]'
python scripts/validate_distribution_review.py \
  examples/validation/calibrex/distribution-review.draft.json
python -m unittest discover -s tests -v
```

[JSON Schema](../schemas/distribution-review.schema.json) は形・必須値・状態を検証し、開発用スクリプトはID重複、参照切れ、スコープ未確定での完了、証拠の種類と対象配布物ハッシュの不一致を検出します。`jsonschema` はテスト・開発用の追加依存で、通常のライセンス検査の実行依存には含めません。

スクリプトの成功は「記録の構造が有効」の意味です。取得元の正当性、ファイルの現在の内容、確認した人物の実在・権限、法的な履行を検証するものではありません。結果は常に `distribution_readiness: not_assessed` であり、未対応が0でも配布承認にはなりません。

受け入れテストでは、mcapのLICENSEだけで対応済みにできないこと、配布範囲未確定や同梱不明を閉じられないこと、実配布物のハッシュが変わると完了証拠が一致しなくなることを確認します。

## 本実装前に決めること

1. ソース公開に含める正確なパスと、確認対象のコミット・アーカイブ。配布形態自体はソース公開に決定済み。
2. 出力と参照元の実ファイルを検証する範囲。手動の確認記録と自動で検証した事実の区別。
3. パッケージ更新・構成変更・条件やレビュー根拠の変更で、どの記録を再確認に戻すか。
4. 必要な対応を決めるためのルールの出典・適用条件と、人の判断が必要な範囲。

これらを固めてから既存CLI・レポートとの接続を行います。収集ZIPの有無や `allowed` だけを配布可能の条件には使いません。
